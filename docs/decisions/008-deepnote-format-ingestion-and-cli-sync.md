# ADR 008: Deepnote Format Ingestion Invalidation — CLI Sync vs. Web UI Git Export

* **Status**: Accepted
* **Date**: 2026-09-01
* **Category**: Diátaxis Explanation / Architectural Decision Record (ADR)
* **Domain**: Artifact Ingestion & Cloud Synchronization Boundaries
* **Updates / Rectifies**: [ADR 002](./002-deepnote-workspace-sync-boundaries.md) and [ADR 007](./007-notebook-format-and-distribution-hierarchy.md)

---

## 1. Context & Problem Statement

[ADR 007](./007-notebook-format-and-distribution-hierarchy.md) established the `.deepnote` YAML format as the primary source of truth for notebook definitions in this repository. However, ADR 007 was authored under a flawed assumption: it assumed that Deepnote Cloud's Web UI Git integration ("Export to GitHub" / "Commit & push") could export native `.deepnote` YAML files directly into a repository.

Empirical testing and container filesystem inspection confirmed this assumption is false:
* **Deepnote Cloud's Web UI Git integration strictly exports `.ipynb` (Jupyter JSON) files.** The web UI contains no toggle, dropdown, or configuration to push native `.deepnote` files.
* Inside the Deepnote container (`~/work/`), native `.deepnote` files exist only in Deepnote's internal storage (`~/work/deepnote/*.deepnote`), while a connected Git repo is cloned into a subfolder (`~/work/<repo-name>/`).

---

### Analysis of the Proof:
1. **Cloud Native Storage (`~/work/deepnote/`)**: Contains `.deepnote` YAML files generated by Deepnote internally.
2. **Git Repository Mount (`~/work/harness-model-config-compiler/`)**: Contains the connected repository where the Web UI Git export exclusively pushes `.ipynb` JSON files into `deepnote/harness-model-config-compiler/`.

---

## 3. Root Cause & Architectural Invalidation

Attempting to rely on the Deepnote Cloud Web UI to generate `.deepnote` files in Git creates an impossible workflow: maintainers would either have to manually copy files between internal container folders (`cp ~/work/deepnote/*.deepnote ~/work/<repo-name>/deepnote/`), which is an unmaintainable anti-pattern, or accept that the UI only produces `.ipynb`.

The only supported, programmatic mechanism for obtaining and synchronizing native `.deepnote` YAML files from Deepnote Cloud is via the **Deepnote CLI / API** (`deepnote sync` backed by `GET /v2/projects/{id}/export` and `POST /v2/projects/{id}/import`).

---

## 4. Reconciling with ADR 002 (Scoped Synchronization)

[ADR 002](./002-deepnote-workspace-sync-boundaries.md) previously highlighted the behavior of `deepnote sync <dir>` and correctly prohibited running *untargeted workspace-wide syncs* into the repository root, which pulled the entire Deepnote organization into a single-tool repo.

We reconcile ADR 002 and ADR 007 as follows:

1. **CLI `deepnote sync` is the Intended Transport for `.deepnote` YAML**:
   * The `.deepnote` format is a CLI/API-level construct, not a Web UI export format.
   * Pulling and pushing `.deepnote` files must be executed via `deepnote sync` (or targeted Deepnote API/MCP interactions) using the `DEEPNOTE_TOKEN` and scoped to the specific target project directory.
2. **Web UI Git Export is Strictly for `.ipynb`**:
   * If maintainers use Deepnote Cloud's web UI "Export to GitHub" or "Commit & push", they must expect downstream `.ipynb` files, not `.deepnote` files.
3. **No Container Manual Copying**:
   * Maintainers and agents must never establish workflows relying on manual file shuffling inside the Deepnote container (`~/work/`).

---

## 5. Consequences

* **Positive**: Eradicates the flawed premise of expecting a `.deepnote` export option in Deepnote's Web UI.
* **Positive**: Grounded in empirical evidence from the live Deepnote execution container.
* **Positive**: Clearly delineates the boundaries: Web UI exports `.ipynb`; CLI `deepnote sync` synchronizes `.deepnote`.
* **Negative**: Synchronizing `.deepnote` files requires a CLI step or MCP automation using an API token rather than a single click in the Deepnote web UI.
